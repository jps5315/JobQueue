1) The queue picks the job with the highest priority first. The data structure used for the waiting jobs is a MaxHeap. The top most element of the waiting queue is picked as the next job. In case of a priority tie the queue defaults to a FIFO order. The time complexity of both adding a new job and picking one from the waiting queue is O(log n).Its because both the operations require a traversal only of a branch of the heap structure. For 1 million queued jobs the complexity of both the operations still remains same. Its because irrespective of the number of jobs the heap structure requires a traversal of one branch.

2) The waiting queue is a synchronous heap structure. It is accessed using a synchronous dispatcher function. The function _runAttempt that runs each job is an asynchronous function that calls the dispatcher when one job settles and a slot is available for the next job. This system used two timers. when a job starts execution a timer is set that aborts the job when its timer expires. For a failed job a backoff delay timer is used that makes a job waiting for a random amount of time in the range (1,2(n-1)). Once the timer expires the job is added back to the main waiting queue. i.e the priority MaxHeap.

3) I hit one bug during timeout. Timeout leads to a job status change to failed and the job is retired after a backoff delay. In my design once the backoff timer of a failed job expires it is assigned a concurrency slot. This led to overshooting the concurrency limit. It happened because when a failed job was waiting for its backoff timer to expire the dispatcher assigned a slot to another job waiting in the queue. When the backoff timer expired the retry job directly gets a concurrency slot that leads to exceeding the limit. I solved this flaw by adding the job back to the waiting queue and making it wait just like its first attempt without assiging it a concurrency slot when its backoff timer expired.

4) If a job function throws synchronously instead of rejecting the dispatcher looks for a try/catch block at the higher levels of the call stack and if it doesn't find one the dispatcher crashes.The dispatcher that directly interacts with the job queue doesn't handle it. Its because the dispatcher handles both the contiditions i.e the concurrency limit and deque from an empty queue by using explicit guardrails that prevent this process from throwing any errors. But the other two processes i.e start and runAttempt executes a job and handles retries so they are asyncronous processes. Both these processes do not crash as they are async and make use of try/catch blocks.If an error is not caught using a try/catch block these prcesses simply return a rejected promise.
